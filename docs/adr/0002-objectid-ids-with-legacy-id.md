# 0002. Member ids become MongoDB ObjectIds

**Status:** Accepted (2026-11-14)

## Context

Legacy ids are sequential `Long`s from a Hibernate sequence; the REST path only matches
`/members/{id:[0-9]+}` and the seed member has id 0. MongoDB has no auto-increment.

## Options

| | Numeric via counter collection | ObjectId |
|---|---|---|
| Generation | `findAndModify` on a counter per insert: extra round trip, single-document hotspot | Generated by the driver, no round trip |
| API contract | Unchanged | Changes: ids become 24-hex strings |
| Migrated data | Ids carry over | Needs a mapping |
| Enumeration | Trivially guessable | Harder to guess (still not a security control) |
| Idiomatic | Fights the database | What MongoDB users expect |

A hybrid keeps ObjectId as `_id` and stores the old id as `legacyId` on migrated documents.

## Decision

`_id` is an ObjectId. Documents migrated from legacy keep their old id in an indexed
`legacyId` field (unique, partial: only migrated documents have it).

## Consequences

- **Intentional API change:** ids in responses and paths are 24-hex strings. Recorded on the
  scorecard; the contract suite reads ids through a per-target format helper.
- A malformed id (`abc`, `-1`) must still return 404, not 400 or 500.
- At scale the deciding factor is external consumers: if other systems store numeric ids, accept
  `legacyId` on the API for a deprecation period.
